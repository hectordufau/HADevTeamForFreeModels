# V3.3 Specification — Engineering Knowledge & Decision Intelligence

**Version:** 3.3.0-draft
**Base:** v3.2.0
**Branch:** feature/v3.3-engineering-knowledge
**Status:** DRAFT — Architecture Review APPROVED WITH REQUIRED ADJUSTMENTS (2026-09-17)

---

## 1. Goals

1. **Structured Engineering Knowledge** — Define a set of core engineering record types (PRD, NFR, DR, ADR, TDR, RSK, SEC, RCA) that capture the engineering history and decision context of the product.
2. **Engineering Knowledge Graph** — Model relationships between records (requirements → decisions → evidence → outcomes) as a queryable graph.
3. **Context Retrieval** — Enable the Harness to retrieve relevant engineering knowledge when making decisions, planning workflows, or reviewing outcomes.
4. **Learning Integration** — Integration only: knowledge informs learning, and learning outcomes update knowledge. No learning system redesign.
5. **Governance** — Authority levels, lifecycle states, and provenance ensure knowledge records are trustworthy and auditable.
6. **Traceability** — Every decision can be traced to the requirements, decisions, and evidence that support it.
7. **Backward Compatibility** — All V3.2 behavior preserved; 729 tests continue to pass.

## 2. Non-Goals

1. **No natural language query** — Free-text knowledge search is deferred to V3.4.
2. **No multi-project knowledge** — Cross-project knowledge sharing is deferred.
3. **No community review workflow** — RFC lifecycle with external review is deferred.
4. **No automated knowledge extraction** — Records are created by humans or structured pipelines, not mined from code.
5. **No knowledge override of governance** — Knowledge is advisory; `PolicyEngine` remains authoritative.
6. **No replacement of V3.2 learning** — V3.3 adds knowledge; it does not replace experiences, strategies, or retrieval.
7. **No Learning Quality optimization** — Experience Quality, Strategy Evolution, Adaptive Exploration, Continuous Learning, and Cross-Task Generalization optimization are FOUNDATION_ONLY. They are candidates for V3.4 — Learning Quality & Optimization.
8. **No learning system redesign** — V3.3 may connect Engineering Knowledge to the existing V3.2 learning system, but must NOT redesign the learning system.

## 3. Terminology

| Term | Definition |
|------|-----------|
| **Engineering Record** | A structured, persistent record of engineering knowledge (PRD, NFR, DR, ADR, TDR, RSK, SEC, RCA) |
| **Engineering Knowledge Graph** | A directed graph of engineering records and their relationships |
| **Provenance** | The origin and history of a record (who created it, when, from what source) |
| **Authority Level** | The trust level of a record (proposed, accepted, deprecated, archived) |
| **Lifecycle State** | The current state of a record in its lifecycle |
| **Traceability** | The ability to link a decision to its supporting requirements, decisions, and evidence |
| **Context Retrieval** | The process of finding relevant engineering records for a given task or decision |
| **Contradiction** | A conflict between two or more records that must be resolved |
| **Knowledge Store** | The persistence layer for engineering records |
| **Decision Context** | The context in which a decision is made, including task, capabilities, policy, experience, strategy, and knowledge |
| **Engineering Knowledge** | What the project explicitly knows, requires, or decided (PRD, NFR, ADR, TDR, RSK, SEC, RCA) |
| **Learning Knowledge** | What the Harness empirically learned from execution (StructuredExperience, FailureLesson, Strategy, DecisionImpact) |
| **Evidence** | What supports or proves claims (test results, verification results, benchmark results, execution artifacts) |

## 4. Record Model

### 4.1 Base Record: `EngineeringRecord`

All record types inherit from `EngineeringRecord`. The architecture review requires a **common core** approach — shared identity, provenance, authority, lifecycle, relationships, versioning, and validation. Avoid eight independent persistence/lifecycle implementations.

```
EngineeringRecord (common core)
        │
        ├── ProductRequirement (PRD)
        ├── NFR
        ├── DecisionRecord (DR)
        │      └── ADR
        ├── TechnicalDebt (TDR)
        ├── Risk (RSK)
        ├── SecurityRecord (SEC)
        └── RCA
```

```python
@dataclass
class EngineeringRecord:
    record_id: str                          # Unique identifier (e.g., "PRD-001", "ADR-042")
    record_type: str                        # "PRD" | "NFR" | "DR" | "ADR" | "TDR" | "RSK" | "SEC" | "RCA"
    title: str                              # Human-readable title
    description: str                        # Full description
    status: str                             # Lifecycle state (see §5)
    authority: str                          # Authority level (see §6)
    provenance: Provenance                  # Origin and history (see §7)
    tags: List[str] = field(default_factory=list)
    created_at: str = field(default_factory=lambda: datetime.utcnow().isoformat())
    updated_at: str = field(default_factory=lambda: datetime.utcnow().isoformat())
    version: int = 1
    superseded_by: Optional[str] = None     # record_id of newer version
    experiment_context: Optional[ExperimentContext] = None  # V3.2 provenance
```

The architecture review requires that PRD NOT be modeled as only one large record. Requirements must be individually addressable.

```python
    priority: str = "medium"                # "critical" | "high" | "medium" | "low"
```

### 4.6 TDR — Technical Debt Record

The architecture review requires TDR to be **first-class** — it must participate in planning, not merely documentation.

- Task touches component → retrieve open TDRs → Planner knows existing debt


## 6. Authority Levels

| Level | Meaning | Who Can Create | Who Can Modify |
|-------|---------|----------------|-----------------|
| `proposed` | Under review | Any agent | Author only |
| `accepted` | Approved, authoritative | Human or governance-approved agent | Author + governance |
| `deprecated` | No longer current | — | Governance only |
| `archived` | Historical record | — | Nobody (immutable) |

**Rule:** Only `accepted` records are authoritative for decision-making. `proposed` records are advisory.

## 8. Graph Relationships

### 8.1 Relationship Types

| From | To | Relationship | Meaning |
|------|----|-------------|---------|
| PRD | NFR | `governs` | PRD is governed by NFRs |
| PRD | ADR | `informs` | PRD informs ADRs |
| NFR | ADR | `constrains` | NFR constrains ADRs |
| DR | PRD | `addresses` | DR addresses a PRD |
| DR | NFR | `satisfies` | DR satisfies an NFR |
| ADR | TDR | `creates` | ADR creates technical debt |
| ADR | RSK | `introduces` | ADR introduces risk |
| ADR | SEC | `enforces` | ADR enforces security |
| RCA | ADR | `motivates` | RCA motivates an ADR |
| RCA | TDR | `identifies` | RCA identifies technical debt |
| TDR | RSK | `creates` | TDR creates risk |
| SEC | NFR | `satisfies` | SEC satisfies an NFR |

### 8.2 Graph Constraints

1. **Acyclic** — The graph must be a DAG (directed acyclic graph)
2. **Typed edges** — Only valid relationship types are allowed
3. **Bidirectional traversal** — From any record, you can find related records in both directions
4. **Contradiction detection** — If two records conflict (e.g., two ADRs with opposite decisions), the graph flags it

- The graph edges are append-only (no deletion, only new edges)
- Provenance log is append-only

## 16. Traceability

### 16.1 Traceability Model

Every decision must be traceable to:
1. **Requirements** — Which PRDs/NFRs govern this decision?
2. **Decisions** — Which DRs/ADRs support this decision?
3. **Evidence** — Which evidence packages support the outcome?
4. **Outcome** — What was the result?

### 16.2 Traceability Query

```python
def trace(self, decision_id: str) -> TraceabilityChain:
    """Build a traceability chain for a decision."""
    chain = TraceabilityChain(decision_id=decision_id)

    # Find the decision record
    decision = self.store.get(decision_id)
    chain.add_decision(decision)

    # Trace to requirements
    for req_id in decision.related_requirements:
        req = self.store.get(req_id)
        chain.add_requirement(req)

    # Trace to evidence
    for ev_id in decision.provenance.evidence_refs:
        ev = self.store.get_evidence(ev_id)
        chain.add_evidence(ev)

    # Trace to outcome
    outcome = self.store.get_outcome(decision_id)
    chain.add_outcome(outcome)

    return chain
```

## 19. Failure Behavior

| Failure | Behavior |
|---------|----------|

## 25. Appendix D: Three Kinds of Knowledge

### A. Engineering Knowledge

**Definition:** What the project explicitly knows, requires, or decided.

**Examples:** PRD, NFR, ADR, TDR, RSK, SEC, RCA

**Characteristics:** Authoritative, versioned, lifecycle-managed, provenance-tracked.

### B. Learning Knowledge

**Definition:** What the Harness empirically learned from execution.

**Examples:** StructuredExperience, FailureLesson, Strategy, DecisionImpact, performance history

**Characteristics:** Empirically derived, confidence-calibrated, subject to revision.

### C. Evidence

**Definition:** What supports or proves claims.

**Examples:** Test results, verification results, benchmark results, execution artifacts, evaluation evidence

**Characteristics:** Immutable, hash-chained, reproducible.

These may reference each other but must not be collapsed into one storage model.

## 26. Appendix E: Knowledge Precedence

```
Governance
    ↓
Security Authority
    ↓
Authoritative Engineering Knowledge
    ↓
Accepted Engineering Knowledge
    ↓
Task Contract / Requirements
    ↓
Verified Evidence
    ↓
Learned Knowledge
    ↓
Exploration
```

### Conflict Semantics

| Conflict | Resolution |
|----------|------------|
| Learned strategy conflicts with Accepted ADR | Learned strategy cannot silently override ADR → conflict detected → proposal to supersede ADR → policy/review |
| Learning outcome contradicts SEC | SEC is authoritative; learning cannot override SEC; flag for review |
| Evidence contradicts Engineering Knowledge | Evidence is authoritative for factual claims; Engineering Knowledge record flagged for update |
| Exploration contradicts Governance | Governance is absolute; exploration is blocked |

## 27. Appendix F: Experimental Design

### 27.1 Experimental Boundary

V3.3 should eventually allow:

```
V3.2 Learning only (BASELINE)
     ↓
vs
     ↓
V3.2 Learning + V3.3 Engineering Knowledge (KNOWLEDGE)
```

This lets field validation measure the actual contribution of Engineering Knowledge. If Learning Quality is simultaneously redesigned, causal attribution becomes much weaker.

### 27.2 Primary Question

Does explicit Engineering Knowledge improve engineering decisions and traceability beyond V3.2 learning alone?

### 27.3 Required E2E Traceability Scenario

A release-critical scenario must demonstrate:

```
PRD → REQ → NFR → ADR → TASK → IMPLEMENTATION → VERIFICATION → EVIDENCE
```

plus TDR / RSK / SEC where applicable.

### 27.4 Required Historical Learning Scenario

Also demonstrate:

```
Failure → RootCauseAnalyzer → RCA → FailureLesson → StructuredExperience → Strategy → Future Task
```
