## 2. Architecture

### 2.1 Class Hierarchy

```
EngineeringRecord (Phase 1)
       │
       ├── ProductRequirement (Phase 4)
       ├── Requirement (Phase 4)
       ├── NFR (Phase 4)
       │
       └── DecisionRecord (Phase 5)
              │
              └── ArchitectureDecisionRecord (Phase 5)
```

ADR is a specialization of DR, not a separate hierarchy. ADR inherits all DR fields and adds architecture-specific fields.

### 2.2 Typed Dispatch

DR/ADR participate in the typed record dispatch system:

```python
# registry.py
TYPED_RECORD_CLASSES = {
    "PRD": PRD,
    "REQ": Requirement,
    "NFR": NFR,
    "DR": DecisionRecord,     # Phase 5
    "ADR": ArchitectureDecisionRecord,  # Phase 5
    # TDR, RSK, SEC, RCA deferred to Phase 6-7
}
```

### 2.3 KnowledgeStore Typed Field Markers

```python
# store.py
_TYPED_FIELD_MARKERS = {
    ...
    "DR": ("decision_type", "context", "rationale"),
    "ADR": ("architecture_domain", "pattern_selected", "trade_offs"),
}
```

When records are saved/loaded, the typed field markers determine whether to dispatch to the typed class constructor.

## 3. DecisionRecord (DR)

### 3.1 Schema

```python
@dataclass
class DecisionRecord(EngineeringRecord):
    record_type: str = "DR"
    status: str = "proposed"
    authority: str = AUTHORITY_PROPOSED

    # DR-specific fields
    decision_type: str = ""       # ARCHITECTURE | TECHNICAL | SECURITY | PRODUCT | OPERATIONAL | DATA | INTEGRATION
    context: str = ""             # The situation requiring a decision
    decision: str = ""            # The decision made
    alternatives: List[Alternative] = []  # Structured alternatives
    rationale: str = ""           # Why this decision (required)
    consequences: Consequences = Consequences()
    related_requirements: List[str] = []  # REQ/NFR/PRD IDs
    related_decisions: List[str] = []     # DR/ADR IDs
```

### 3.2 Lifecycle

```
proposed → accepted → deprecated → superseded → archived
    │
    └── (agent-generated always starts as proposed)
```

Terminal: archived

### 3.3 Decision Types

Seven decision types are valid:
- ARCHITECTURE — overall system structure
- TECHNICAL — technology choices, frameworks
- SECURITY — security-related constraints
- PRODUCT — feature/behavior decisions
- OPERATIONAL — operational/procedural decisions
- DATA — data storage, schema, migration
- INTEGRATION — external system integration

### 3.4 Completeness Validation

Required for DR completeness:
- `has_context` — non-empty context string
- `has_decision` — non-empty decision statement
- `has_rationale` — non-empty rationale (completeness violation if missing)
- `has_decision_type` — one of VALID_DECISION_TYPES
- `has_provenance` — provenance present and complete
- `valid_requirements` — all references to REQ/NFR/PRD IDs
- `valid_decisions` — all references to DR/ADR IDs

**Missing rationale = completeness violation.** Explicitly checked in validate().

### 3.5 No Fabricated Alternatives

Empty alternatives list is valid (only one option evaluated). Distinguishes:
- **No alternatives recorded** — `alternatives=[]` is valid if only one option was evaluated
- **Alternatives evaluated and rejected** — structured with disposition (SELECTED/REJECTED)

No fabrication: the system never creates fake alternatives to satisfy completeness.

## 4. ArchitectureDecisionRecord (ADR)

### 4.1 Schema (extends DR)

```python
@dataclass
class ArchitectureDecisionRecord(DecisionRecord):
    record_type: str = "ADR"
    status: str = "proposed"       # Always proposed for agent generation
    authority: str = AUTHORITY_PROPOSED
    decision_type: str = DECISION_TYPE_ARCHITECTURE  # Default

    # ADR-specific fields
    architecture_domain: str = ""     # data | api | security | deployment | messaging | ui | infrastructure
    patterns_considered: List[str] = []
    pattern_selected: str = ""
    trade_offs: str = ""
    impact: str = ""
```

### 4.2 ADR Lifecycle

```
proposed → accepted → deprecated → superseded → archived
```

Identical to DR lifecycle. Terminal: archived.

### 4.3 Architecture Domains

Valid domains:
- DATA — data storage, schema
- API — API design, endpoints
- SECURITY — authentication, authorization
- DEPLOYMENT — deployment topology
- MESSAGING — message queues, events
- UI — user interface architecture
- INFRASTRUCTURE — infrastructure decisions

### 4.4 Agent Generation ≠ Acceptance

**Critical invariant:** Agent-generated ADR always starts as PROPOSED. Never automatically ACCEPTED.

```python
def __post_init__(self):
    # New ADRs default to PROPOSED, but reconstructed records preserve status
    if not self.status:
        self.status = "proposed"
    if not self.authority:
        self.authority = AUTHORITY_PROPOSED
    ...
```

This is enforced even when all fields are complete. Acceptance requires explicit lifecycle transition (human/governance action).

### 4.5 ADR Completeness

DR completeness plus ADR-specific:
- `has_architecture_domain` — one of VALID_ADR_DOMAINS
- `has_patterns` — patterns_considered non-empty
- `has_pattern_selected` — pattern_selected non-empty
- `has_trade_offs` — non-empty trade-offs statement
- `has_impact` — non-empty impact statement

Requiring pattern_selected when patterns are considered prevents claiming to consider alternatives without selecting one.

## 6. Supersession

### 6.1 Supersede Chain

Supersession = new decision replaces previous. Creates SUPERSEDES relationship.

```python
adr1.supersede("ADR-004")   # ADR-001 superseded_by ADR-004
adr1.add_relationship("ADR-004", RELATIONSHIP_SUPERSEDES)
```

### 6.2 Version vs Supersession

- **Version:** ADR-005 v1 → ADR-005 v2 = same logical decision evolved (increment version, same record_id)
- **Supersession:** ADR-001 → ADR-006 = new decision replaces previous (new record + SUPERSEDES edge)

Tests prove version != supersession.

### 6.3 Supersession Conflict Detection

```python
find_supersession_conflicts(records) → List[Conflict]
```

Detects:
- **MUTUAL_SUPERSESSION:** A supersedes B, B supersedes A (both directions in `superseded_by` or relationships)
- **AMBIGUOUS_SUCCESSOR:** A supersedes multiple records (multiple SUPERSEDES outgoing edges)
- **SUPERSESSION_CYCLE:** supersession chain forms a cycle

Fail-closed: ambiguous topology returns `None` for effective decision.

### 6.4 Effective Decision

```python
get_effective_decision(record_id, record_map) → Optional[str]
```

Returns the last record in the chain (most recent), or None if ambiguous.

## 7. Graph Integration

### 7.1 Relationship Types Used

| From | To | Relationship | Meaning |
|------|----|-------------|---------|
| DR | REQ/NFR/PRD | DECIDED_BY | DR addresses requirement |
| DR | DR/ADR | RELATES_TO | DR relates to other decisions |
| ADR | REQ/NFR/PRD | DECIDED_BY | ADR addresses requirement |
| ADR | DR/ADR | RELATES_TO | ADR relates to other decisions |
| ADR | ADR | SUPERSEDES | ADR supersedes previous ADR |
| ADR | EV-ID | SUPPORTED_BY | ADR supported by evidence |
| ADR | ADR | CONTRADICTS | ADR contradicts another ADR |

### 7.2 Helper Methods

```python
dr.link_requirement("REQ-001")     # Adds DECIDED_BY relationship
dr.link_decision("ADR-001")        # Adds RELATES_TO relationship
adr.supersede("ADR-002")           # Sets superseded_by + SUPERSEDES relationship
adr.add_relationship("EV-001", RELATIONSHIP_SUPPORTED_BY)  # Evidence link
```

## 9. ADRAutomation Migration

### 9.1 Classification

| Behavior | Classification | Rationale |
|----------|---------------|-----------|
| `record_decision()` | MIGRATE | Now creates canonical ArchitectureDecisionRecord |
| `get_relevant_adrs()` | ADAPT | Queries KnowledgeStore, falls back to memory |
| Memory storage | KEEP TEMPORARILY | Preserved for backward compatibility |

### 9.2 Adapter Pattern

```
legacy ADRAutomation → adapter → Engineering Knowledge ADR (canonical)
                     ↓
                   Memory (reference only, no canonical truth)
```

The ADRAutomation class now:
1. Creates `ArchitectureDecisionRecord` stored in KnowledgeStore
2. Also stores via legacy MemoryManager path (backward compat)
3. Returns markdown file path (preserves old API return value)
4. `get_relevant_adrs()` queries KnowledgeStore, falls back to memory

### 9.3 No Competing Canonical Store

Architecture decision: **Engineering Knowledge ADR = canonical ADR.**

Legacy ADRAutomation remains as a compatibility adapter, not as two independent ADR stores. Memory may reference ADRs but never contains independent ADR canonical truth.
