## 2. Current runner default configuration

- `FieldExperimentConfig` (harness/validation/field_validation.py, formerly lines
  626-628) had defaults `train_reps=3, validation_reps=3, test_reps=3`.
- `scripts/phase8_field_validation.py --reps` defaulted to **3** (line 110).

So a plain `python3 scripts/phase8_field_validation.py` ran reps=3 → n=30, producing the

## 3. Question-by-question findings

### Q1. What exact configuration produced the accepted Phase 8 run? Repetitions 5? Where persisted?
Repetitions 5/5/5, seed 314159, run id `V3.2-FV8-20260911`. Persisted in the protected
release artifact `artifacts/v3.2-release/field_validation/results.json` and in the accepted
docs. Restored exactly, the run reproduces bit-for-bit (§5).

### Q2. Was repetitions=5 persisted anywhere?
Yes — `results.json` (`repetitions: {train:5, validation:5, test:5}`) and the doc headers
(`Reps: 5/5/5`). The **problem** was that the *default* execution path (CLI + dataclass)
used a hidden fallback of **3**, so any minimal re-run silently used reps=3. The 5 lived in
the result artifact, not in the default configuration.

### Q3. Why does the current runner default to repetitions=3?
Both the `FieldExperimentConfig` dataclass and the CLI `--reps` default were set to 3 as a
historical default; the accepted run used 5 explicitly. There was no single authorititative
source — a **repetition-configuration ambiguity** (default 3 vs accepted 5).

### Q4. Is the accepted run reproducible when the original config is restored exactly?
**YES.** With reps=5, seed 314159, run id `V3.2-FV8-20260911` restored exactly, two FRESH
processes both produced COLD 36.0% / NO_EXPL 72.0% / EXPL 78.0%, scores 0.4573/0.589/0.626,
n=50 — identical to the accepted report. (See evidence matrix §6.)

### Q5. Does load_benchmark_tasks() mutate the benchmark corpus in-place?
**YES — confirmed defect.** `load_benchmark_tasks()` (formerly line 214) copied the task
*lists* with `list(...)` but not the task *dicts*, then wrote `t["category"]` and
`t["difficulty"]` directly onto the module-level `runner.TRAIN_TASKS` /
`VALIDATION_TASKS` / `TEST_TASKS` singletons. Probe result:

```
FRESH corpus before any load: difficulty histogram = {medium:18, high:21, low:1}
after load call #1:            difficulty histogram = {0.5:18, 0.72:21, 0.3:1}
after load call #2:            difficulty histogram = {0.55:40}   <-- ALL tasks corrupted
after load call #3:            difficulty histogram = {0.55:40}
```

Because `DIFFICULTY_PRIOR = {"low":0.30,"medium":0.50,"high":0.72}` and the already-numeric
values from call #1 are not keys on the second call, every task falls back to **0.55**.

### Q6. Can repeated calls in the same process alter subsequent outcomes? Test.
**YES — confirmed.** Two full runs in the SAME process with identical config produced
different results (`Same-process identical: False`; 600/600 observations differed),
because the second run's `load_benchmark_tasks()` saw the corrupted all-0.55 corpus. This is
the deterministic bug fixed here.

### Q7. Does a fresh process with identical persisted inputs produce identical results?
**YES for cross-process (with the fix), and for first-run-in-fresh-process (before/after).**
With identical run id + seed + reps, fresh processes reproduce exactly. Note: the
`validation_run_id` is deliberately folded into the per-execution seed (derived via SHA-256,
never Python `hash()`), so **different run ids are different deterministic draws** — a run
only reproduces bit-for-bit when the SAME run id is used (which is correct provenance
behaviour: the run id is persisted with every observation and in results.json).

### Q8. Does the dataset digest remain stable before and after task loading?
**YES.** `dataset_digest()` = `569acf1dc759329d` before, after the 1st, 2nd and 3rd load
(and across processes). The digest deliberately hashes only identity + category fields (not
the mutated `difficulty`), so the mutation did not show up in the digest — one reason the
defect went unnoticed.

### Q9. Does task ordering change after repeated loading?
**NO.** Task ordering within each split is preserved across repeated loads and matches the
source order (TEST-001…TEST-010, etc.). (New test I4.)

### Q10. Does difficulty injection affect outcome generation, routing, evaluation, or digest calculation?
- **Outcome generation:** YES — `_outcome_model` reads `task["difficulty"]`. The first load
  maps string→prior (correct); the second load collapsed all to 0.55, changing outcome draws.
  This is exactly what made same-process repeat runs diverge.
- **Routing/evaluation:** affected transitively (different outcomes → different aggregated /
  statistical outputs).
- **Digest calculation:** NOT affected — `dataset_digest()` excludes difficulty.
- **Configuration digest:** `configuration_digest()` covers significance + exploration only;
  not affected by difficulty.

## 4. Root cause

Two related defects, both addressed:

1. **Repetition-configuration ambiguity (primary driver of the observed live divergence).**
   The accepted result used reps=5; the default execution path silently used reps=3. The
   "current live reproduction" (COLD 36.67% / NO_EXPL 63.33% / EXPL 66.67%, n=30) is exactly
   the accepted config with reps set to 3 — same seed, same run id, same dataset digest.
   Root fix: a single authoritative `field_validation.repetitions` source
   (`DEFAULT_REPETITIONS = 5` + `resolve_repetitions()`), consumed by the CLI, runner,
   report generator, machine-readable results and release evidence.

2. **`load_benchmark_tasks()` in-place, non-idempotent mutation of the shared corpus.**
   Confirmed: the first call mutated the global `runner.TRAIN_TASKS/VALIDATION_TASKS/TEST_TASKS`
   singletons (string difficulty → numeric), and the second call collapsed every task to
   difficulty 0.55. This caused **first-run-vs-subsequent-run divergence within one process**
   and violated the "source corpus must remain immutable" invariant. Root fix: build per-call
   copies (`task = dict(original)`), always read `difficulty` from the original, never mutate
   the source.

Both defects were reproduced empirically and the fixes verified (see §7).

## 7. Post-fix verification

### 7.1 load_benchmark_tasks() idempotency / immutability (fixed)
```
FRESH corpus before any load: difficulty histogram = {medium:18, high:21, low:1}
after load call #1:            difficulty histogram = {medium:18, high:21, low:1}  (source unchanged)
after load call #2:            difficulty histogram = {medium:18, high:21, low:1}  (source unchanged)
after load call #3:            difficulty histogram = {medium:18, high:21, low:1}  (source unchanged)
TRAIN-001 difficulty across calls: call1=0.5 call2=0.5 call3=0.5   (idempotent)
TRAIN-004 difficulty across calls: call1=0.72 call2=0.72 call3=0.72 (idempotent)
```
The source corpus is now never mutated; repeated calls are semantically identical.

### 7.2 Same-process reproducibility (fixed)
`Same-process identical (I5): True` — two full runs in one process now produce identical
observations (previously False).

### 7.3 Cross-process reproducibility (fixed final run)
Final release run `V3.2-FV8-20260912-reprod` (reps 5, seed 314159) reproduced exactly in a
second fresh process:
- COLD 0.42 (0.4437) / NO_EXPL 0.74 (0.5842) / EXPL 0.82 (0.6331), n=50, digest 569acf1dc759329d.

### 7.4 Canonical repetition configuration (fixed)
`DEFAULT_REPETITIONS = 5`; `resolve_repetitions(None) → 5`, `→3 → 3`, `→5 → 5`.
CLI default is now `None → 5` (verified: `phase8_field_validation.py` prints `Reps
(train/val/test): 5/5/5`). The runner, CLI, report generator, results.json and the new
release artifact all consume the resolved value; results.json now carries
`resolved_configuration {repetitions, seed, exploration_rate, significance, split_policy,
variance_policy}` plus `dataset_digest`, `configuration_digest`, `code_revision`.

## 9. Classification

**R-B — Reproducible After Deterministic Bug Fix.**

Rationale:
- The accepted result (36/72/78, n=50) is **fully reproducible** from the exact recorded
  inputs (same run id + seed + reps → bit-identical, verified in two fresh processes).
- However, **two deterministic defects are confirmed** and fixed:
  1. `load_benchmark_tasks()` in-place, non-idempotent mutation of the shared benchmark
     corpus (second call collapses all difficulties to 0.55 → same-process repeat runs
     diverge; source-corpus immutability invariant violated).
  2. Ambiguous repetition default (runner/CLI default 3 vs accepted 5) → the observed live
     divergence (n=30 vs n=50).
- Per the R-B contract, a confirmed deterministic bug is fixed and the benchmark **must be
  rerun** after the fix; the prior numbers **cannot remain the release numbers** (though they
  are provably reproducible, they predate the fix). A new final run
  (`V3.2-FV8-20260912-reprod`, §7.3) has been executed on the corrected code as durable
  release evidence and is marked as superseding the prior run.
