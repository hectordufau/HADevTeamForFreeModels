## 2. COLD vs LEARNED Mode Specification

### 2.1 COLD Mode

- **No experience retrieval.** `MultiFactorRetriever` returns empty results.
- **No strategy application.** `StrategyStore.find_by_task_class()` returns nothing.
- **No exploration.** `AdaptiveModelPolicyV3` uses purely random selection from free models.
- **No learning feedback.** After COLD execution, nothing is stored in ExperiencePipeline or StrategyStore.
- **Evidence IS recorded** (for audit trail) — evidence_store still stores CanonicalExecutionRecord.
- **Result: A clean baseline** showing what the system does without any accumulated knowledge.

### 2.2 LEARNED Mode

- **Full retrieval.** `MultiFactorRetriever` runs with all factors.
- **Strategy generation.** After each batch, `StrategyGenerator.generate()` runs.
- **Adaptive exploration.** `AdaptiveModelPolicyV3` uses confidence-based exploration.
- **Learning feedback loop.** Post-execution, experiences, strategies, and performance data are stored.
- **Full evidence recording.**
- **Result: Cumulative learning** — each run builds on all prior runs.

### 2.3 Mode Enforcement Rules

1. **No cross-mode data leakage.** LEARNED-mode data must never enter COLD-mode retrieval.
2. **All artifacts must be tagged with mode.** Every stored object (experience, strategy, profile, evidence) gets a `mode: "COLD" | "LEARNED"` field.
3. **Storage isolation.** All artifact directories should be either mode-namespaced (`artifacts/cold/`, `artifacts/learned/`) or filtered at read time.
4. **Identical initial conditions.** Both modes start with the same model catalog, agent registry, and capability taxonomy.

## 5. Recommended TRAIN/VALIDATION/TEST Split Strategy

### 5.1 Task Separation Dimensions

Split tasks across 3 orthogonal dimensions:

1. **Capability domain.** Which capabilities are exercised.
2. **Difficulty level.** Simple (1–2 capabilities) → Complex (4+ capabilities, integration).
3. **Task novelty.** How similar the task is to anything in the training set.

### 5.2 Split Criteria

| Split | Capability Coverage | Difficulty Mix | Novelty | Overlap with TRAIN |
|-------|-------------------|----------------|---------|-------------------|
| WARMUP | Broad, 1–2 caps each | Low–Medium | All unseen | Disjoint |
| TRAIN | 10 caps, varied combos | Balanced | Core tasks | Self |
| VALIDATION | Subset of TRAIN caps | Medium | Different specifics | Same domain, different task |
| TEST | Novel combinations | Medium–High | Unseen domain pairs | 0 overlap |

From the existing 12 scenarios (BM-P001 through BM-P012) + new scenarios for field validation:

## 6. How Decision Influence Is Currently Tracked

### 6.1 Existing Tracking Infrastructure

The `DecisionImpactTracker` in `v3_integration.py` is the primary mechanism:

```python
class DecisionImpact:
    decision_id: str
    context_id: str
    decision_type: str  # model, agent, workflow, capability
    baseline_choice: str
    actual_choice: str
    influenced_by_learning: bool
    outcome_improved: Optional[bool]
    score_delta: float
```

**Where it's recorded:**
1. `UnifiedDecisionPipeline.decide_model()` — records when strategy suggests a different model
2. `UnifiedDecisionPipeline.decide_plan()` — records when strategy suggests a different workflow
3. Stored in `artifacts/decisions_v31/` as individual JSON files

**Where it's consumed:**
1. `DecisionInfluenceMetric.calculate()` in `evaluation.py` — reads the decision log
2. `DecisionImpactTracker.get_summary()` — basic aggregation

### 6.2 Gaps for Field Validation

1. **Decision logging is incomplete.** `decide_agent()` records a `DecisionImpact` but doesn't save it to the tracker.
2. **`outcome_improved` is mostly null.** It's only set via `record_outcomes()`, which requires an external caller. In field validation, each decision must be paired with the execution outcome.
3. **In-memory list + file store.** `DecisionImpactTracker._impacts` is in-memory and loaded only per-instance. If the tracker is re-instantiated, old impacts from files aren't loaded back into `_impacts`.
4. **No mode discrimination.** Tracked decisions don't carry a COLD/LEARNED marker.
5. **Baseline choice is not systematically populated.** `decide_model()` sets `baseline_choice` from the model_policy selection, but `decide_plan()` hard-codes `"default"` — not the actual non-learning baseline.

### 6.3 Recommended Fixes

1. Add `mode` field to `DecisionImpact`
2. Add `validation_run_id` field for grouping
3. Make `DecisionImpactTracker.__init__` load all persisted impacts into `_impacts`
4. Wire `record_outcomes()` into the benchmark execution loop
5. In COLD mode, always store baseline decisions even without learning influence (for comparison)

## 7. Contamination Prevention Strategy

### 7.1 Sources of Contamination

| Source | Risk | Mitigation |
|--------|------|------------|
| LEARNED experiences leaking into COLD retrieval | HIGH | Separate storage directories per mode; mode-aware filter on all retrieval paths |
| Strategy store populated from LEARNED runs used in COLD decision pipeline | HIGH | StrategyStore returns empty results in COLD mode |
| Model profiles updated by LEARNED runs skewing COLD model selection | MEDIUM | Separate ModelProfileStore instances per mode |
| Performance registry V3 accumulating LEARNED samples that affect COLD rank_models | HIGH | Separate PerformanceRegistryV3 instances per mode |
| File-system collisions (same artifact path used by both modes) | MEDIUM | Namespace all artifact dirs by mode (cold/ vs learned/) |

### 7.2 Concrete Strategy

1. **Two entirely separate harness instances.** COLD and LEARNED modes get their own `ExperienceStore`, `PerformanceRegistryV3`, `StrategyStore`, `ModelProfileStore`, `EvidenceStore`, and `DecisionImpactTracker`.
2. **Separate artifact directories.** All stores point to `artifacts/cold/` or `artifacts/learned/`.
3. **Single shared non-learning infrastructure.** Capability taxonomy, agent registry, model catalog — these are static and shared.
4. **Verification pass.** After the COLD run, verify the artifact trees contain no LEARNED artifacts and vice-versa.
5. **Start state snapshot.** Before each mode, snapshot the config and source tree to a manifest. After each mode, verify no files changed outside allowed paths.

### 7.3 Post-Contamination Recovery

If contamination is detected:
1. Flag the affected runs
2. Re-run those runs from a clean state with isolated stores
3. Document the contamination event in the report

## 8. Risk Assessment

| Risk | Probability | Impact | Mitigation |
|------|------------|--------|------------|
| COLD/LEARNED data leakage through shared stores | HIGH | CRITICAL | Separate store instances per mode; verification pass |
| Insufficient statistical power (3× repetition) | MEDIUM | HIGH | Use bootstrap confidence intervals; report effect sizes |
| Random variance swamping learning signal | MEDIUM | HIGH | Seed-controlled runs; matched pairs design |
| Task difficulty imbalance between splits | LOW | MEDIUM | Stratify by difficulty metric; verify balance in report |
| Exploration in LEARNED mode triggers non-reproducible decisions | MEDIUM | MEDIUM | Fix random seeds per run; log seed in decision trace |
| Benchmark scenario quality insufficient | LOW | MEDIUM | Review each scenario manually before running |
| Evidence store disk I/O becoming bottleneck at 260 executions | LOW | LOW | Evidence store is lightweight JSON — 260 executions is small |
