## 4. Architecture

### 4.1 E2E Architecture

The golden scenario uses REAL V3.3 components to construct and verify each step:

```
PRD → REQ → NFR → ADR → TDR/RSK/SEC → Task →
Knowledge Retrieval → Plan → Policy → Execution →
Verification → Evidence → Review → Learning → Future Decision
```

- All 23 steps have stable IDs and deterministic digests
- Policy evaluation uses `KnowledgePolicyEngine`
- Review uses `KnowledgeReviewer`
- Knowledge retrieval uses `KnowledgeRetriever` against the REAL KnowledgeStore
- Learning is recorded (KNOWLEDGE_PLUS_LEARNING only)

### 4.2 Experimental Architecture

```
KnowledgeValidationRunner.run_all()
├── CONTROL (knowledge_on=False, learning_on=False)
│   └── Fixed baseline competence, no retrieval
├── KNOWLEDGE_ONLY (knowledge_on=True, learning_on=False)
│   └── Knowledge boost from real KnowledgeStore retrieval
└── KNOWLEDGE_PLUS_LEARNING (knowledge_on=True, learning_on=True)
    └── Knowledge boost + learning benefit from KnowledgeLearningBridge
```

Each mode gets:
- Separate `ModeKnowledgeStore` (in-memory SQLite, unique db_path per mode)
- Separate learning store (only KNOWLEDGE_PLUS_LEARNING has `ExperiencePipeline`)
- Separate executor with isolated `_strategy_store`
- Separate artifact namespace: `artifacts/v3.3/<run_id>/<mode>/`

## 20. Known Limitations

1. **Outcome model is deterministic simulation** — competence is derived from actual knowledge records but the score/latency model uses bounded random bands (same approach as V3.2 field validation and V3.1 SimulatedExecutor)
2. **Cross-mode statistical pairing** relies on `EvaluationObservation.match_key()` which includes config JSON; since `knowledge_enabled`/`learning_enabled` flags differ between modes, cross-mode pairing rate is 0 by design — statistics are computed as UNPAIRED comparisons
3. **Knowledge provenance timestamps** differ between modes (each `_seed_knowledge` call creates fresh `Provenance` objects with `datetime.utcnow()`), so knowledge digests match in content but not in byte-for-byte digest comparison
4. **Learning store benefit** is derived from deterministic strategy promotion, not from a trained model — the `learning_benefit_per_strategy` constant (0.10) modulates the effect
5. **Golden scenario step digests** include `compute_hash()` of records with `datetime.utcnow()` timestamps in provenance, so full-trace byte-for-byte determinism is limited to step types/statuses/IDs (which are stable)
