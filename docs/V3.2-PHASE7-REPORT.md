# V3.2 Phase 7 Report — Failure-Derived Learning Integration

**Date:** 2026-09-11
**Branch:** `feature/v3.2-learning-integrity`
**Base:** v3.1.0 + V3.2 Phases 1–6
**Scope:** Phase 7 ONLY (spec §11). Phase 8 NOT implemented, no release/tag,
no merge to master, no historical artifact deleted or modified.

## Summary

Phase 7 closes the failure-learning gap. Failures now flow through the
canonical V3.2 pipeline — **StructuredFailure → RootCauseAnalyzer →
FailureToLearningPipeline → StructuredExperience → V3.2 ExperienceStore →
Retrieval/Strategy → Future Decision** — using the *same* namespaced,
ExperimentContext-isolated storage and retrieval as every other V3.2
experience. No parallel architecture was created.

The three defining properties are:

1. **Fail-closed TEST suppression** — a TEST-mode failure produces *evidence only*
   (`failure_evidence/`), never a training `StructuredExperience`. The TEST
   experience store stays empty. Not merely filtered at retrieval — the derived
   experience is never created.
2. **COLD immutability** — a COLD-mode failure produces evidence and analysis but
   performs **NO mutation** of the COLD learning/baseline state. Task N's COLD
   failure can never make task N+1 learned.
3. **LEARNED failure learning** — LEARNED / LEARNED_NO_EXPLORATION /
   LEARNED_EXPLORATION mode failures derive a `StructuredExperience` with full
   provenance, a stable SHA-256 identity, and an inspectable
   failure→lesson→experience→strategy→decision chain, subject to normal
   security/governance (advisory-only) policies.

Full suite: **698 passed** (677 baseline + 21 new Phase 7 tests, 0 regressions).
All **29 git-tracked historical artifacts remain intact (29 → 29)**. Phase 5 and
Phase 6 empirical/reproducibility results are byte-for-byte identical to prior
phases.

## 1. Canonical pipeline (no parallel architecture)

The existing `FailureToLearningPipeline` (in `harness/planner/failure_intelligence.py`)
was **integrated**, not forked. When a V3.2 `ExperimentContext` is supplied it
now emits the same `StructuredExperience` type and stores through the same
`ExperiencePipeline` (`harness/learning/experience.py`) used by all other V3.2
experiences, namespaced under `artifacts/v3.2/<run_id>/<mode>/experiences/`.

```
StructuredFailure
   └─> RootCauseAnalyzer            (taxonomy: category/sub_category/severity)
   └─> FailureToLearningPipeline
         ├─> FailureLesson          (failure_category, summary, root_cause,
         │                           corrective_action, prevention_strategy)
         ├─> StructuredExperience   (source_type=failure, provenance, evidence_refs)
         └─> ExperiencePipeline     -> V3.2 ExperienceStore (namespaced per context)
   └─> MultiFactorRetrieval / Strategy / Decision (advisory, tracked)
```

## 2. Failure provenance (spec §11.2)

Every failure-derived experience preserves the full provenance set
(`source_type`, `source_task_id`, `source_execution_id`, `validation_run_id`,
`benchmark_id`, `mode`, `failure_id`, `failure_category`, plus optional
`evidence_refs`, `verification_refs`, `decision_refs`, `strategy_refs`,
`model_id`, `agent_id`, `capabilities`). Fields that are genuinely absent are
recorded as `""`/empty — never fabricated. The `StructuredExperience` carries a
`provenance` dict and explicit `source_type`/`failure_id`/`failure_category`
attributes.

## 3. Stable failure identity (spec §4)

Stable ID derivation **never uses Python's `hash()`** (process-randomized). The
failure-experience ID is a deterministic **SHA-256** over the failure ID plus
the experiment context:

```
fexp_<sha256(f"{failure_id}::{mode}::{validation_run_id}::{benchmark_id}::{task_id}")[:16]>
```

The same failure + context maps to the same canonical record **across process
restarts**. Verified by a real subprocess re-derivation test (R8) and by the
evidence script (`stable id re-derived = True`).

## 4. Fail-closed TEST (spec §11.3, task §6) — HARD requirement

A TEST-mode failure **never becomes a training experience**. In
`FailureToLearningPipeline.process()`, TEST short-circuits *before* any
`StructuredExperience` is built or stored. The evidence is recorded in the
TEST artifact namespace only:

```
artifacts/v3.2/V3.2-P7-20260911/TEST/failure_evidence/fexp_e6f91858e4d5e32b.json
```

Evidence record (release-critical negative evidence):
```
suppression_reason = TEST
learning_suppressed = True
training_mutation = False
```
And the TEST experience store is **empty**:
```
artifacts/v3.2/V3.2-P7-20260911/TEST/experiences/  -> (no files)
```
Additionally, `ExperiencePipeline.process_stored()` rejects a TEST-mode context
with a `ValueError`, so even a direct store attempt is blocked (defense in
depth).

## 5. COLD immutability (task §7)

A COLD-mode failure records evidence + analysis but performs **no mutation** of
the COLD baseline learning state:

```
artifacts/v3.2/V3.2-P7-20260911/COLD/failure_evidence/fexp_cd2b8fffec17faf5.json
   suppression_reason = COLD, training_mutation = False
```

The COLD `experiences/` namespace contained only the hand-placed baseline marker
`COLD-P7-BASELINE.json` (a manual control inserted to prove immutability); after
processing the COLD task-N failure the directory still contains **only that
marker** — no new experience file. The baseline file's bytes are byte-for-byte
unchanged. A COLD task N+1 failure is independently suppressed
(`experience_id = None`), so COLD task-N failure → learning → task N+1 learned
is impossible.

> Note: the COLD baseline marker is a test control, not a failure-derived
> experience; COLD itself stores no learned experiences in real operation.

## 6. LEARNED failure learning (task §8)

`LEARNED`, `LEARNED_NO_EXPLORATION`, and `LEARNED_EXPLORATION` modes all derive
and store failure `StructuredExperience`s, governed by normal policies
(parametrized unit test covers all three). Evidence example (mode
`LEARNED_EXPLORATION`):

```

source_task_id     = TASK-P7-A
source_execution_id= exec-p7-a

benchmark_id       = BENCH-FAIL-P7
source_type        = failure
mode               = LEARNED_EXPLORATION

confidence         = 0.8
```

## 7. Isolation (task §9)

Every failure-derived experience is isolated by `ExperimentContext`:

- **run A ≠ B**: an experience stored under run `RUN-A` is NOT retrievable under
  `RUN-B` (namespaced path).
- **COLD ≠ LEARNED**: LEARNED failure experiences are not retrievable in a COLD
  context.
- **TEST → never training**: TEST writes only `failure_evidence/`; the
  `verify_isolation` scan shows 0 TEST-in-training contamination.

## 8. Dedup / idempotency (task §10)

Same `failure_id` + context → same stable `experience_id`, stored under a
task-keyed path, so re-processing over-writes the same canonical file. Verified
twice / thrice / after re-derivation: **exactly 1 canonical record**
(`idempotent canonical records = 1`). The restart idempotency test
(`test_restart_idempotency_subprocess`) re-derives the identical ID in a fresh
Python process via SHA-256.

## 9. Failure lesson quality (task §11)

The Failure → Analysis → Lesson → Experience → Strategy chain is preserved by
the new `FailureLesson` dataclass (`failure_category`, `summary`, `root_cause`,
`corrective_action`, `prevention_strategy`, `root_cause_known`). Unknown root
cause is recorded as **UNKNOWN / known=False** and never invented
(`test_unknown_root_cause_honest`).

## 10. Security / governance safety (tasks §12, §13)

- **Security failures** produce defensive-only lessons (`validate earlier`,
  enforce safe selection). Forbidden transformations — "gate failed→disable",
  "denied→increase autonomy", "rejected→bypass" — are blocked; any weakening
  suggestion present in the input is **detected and neutralized**, and the raw
  directive is never echoed into the persisted lesson (`[5b]` evidence:
  `weakening detected=True`, `neutralized lesson=True`).
- **Governance** is never weakened: no failure-derived lesson disables a gate,
  expands autonomy, removes review, changes tool perms, the free-model
  invariant, or a forbidden-change rule. All learning is **advisory**; the
  `advisory_only` / `governance_preserved` flags assert this, and `PolicyEngine`
  remains authoritative.
- Evidence example ([5]): `advisory_only=True`, `governance_preserved=True`,
  `security_defensive=True`, `weakening_constraint=False` for a clean defensive
  security lesson.

Task B (related) retrieved the failure-derived experience and its decision was
marked `learning_influenced = True`. Decision attribution follows Phase 4
semantics (attribution is *not* auto-CONFIRMED; `attribution_level` stays at the
caller-set value, default `NONE` until evidence supports a higher level).

## 12. Failure avoidance (task §15)

`failure_avoidance_metric()` feeds the Failure Avoidance metric and preserves
**comparative vs causal**: only retrieval-influenced avoidance is counted as
causal; a simple later success is never counted as causal avoidance. Evidence:
`avoidance_rate = 1.0 (causal=True)` for the demonstrated case; the unit test
asserts 0.0 for the no-avoidance case.

## 13. Determinism / reproducibility (tasks §17, §18)

- Identical inputs → identical lesson, experience, stable ID, retrieval →

  `lesson`, and `confidence` across two independent pipeline instances.
- No evaluation→learning feedback created (failure learning is write-once on
  the failure event; Phase 5's evaluation pipeline remains read-only).
