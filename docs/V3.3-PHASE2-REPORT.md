## 5. Architecture Decisions

### 5.1 Storage Engine

SQLite with WAL (Write-Ahead Logging) mode for:
- ACID transactions
- Atomic writes (no partial records)
- Process restart durability
- Concurrent read support

### 5.2 Canonical Representation

Each `EngineeringRecord` is stored as a JSON BLOB in the `engineering_records` table with:
- `record_id` (TEXT, PRIMARY KEY)
- `record_type` (TEXT, indexed)
- `status` (TEXT, indexed)
- `authority` (TEXT, indexed)
- `version` (INTEGER)
- `data` (TEXT — canonical JSON serialization)
- `integrity_hash` (TEXT — SHA-256 of canonical data)
- `created_at`, `updated_at` (TEXT — ISO 8601 timestamps)

### 5.3 Index Architecture

SQLite indexes on derived columns (record_type, status, authority) support indexed lookups.
Indexes are derived data — canonical records remain source of truth.
`rebuild_indexes()` rebuilds from canonical records.

### 5.4 Integrity Verification

SHA-256 hash stored on save, recomputed and compared on get.
Tampering with the JSON blob raises `IntegrityError`.
Corrupt records are excluded from decision use.

### 5.5 Reload Behavior

`reload()` closes and reopens the SQLite connection.
All persisted records, versions, authority, provenance, and relationships survive process restart.

### 5.6 Search

Case-insensitive substring search on title and description fields.

## 10. Known Limitations

1. **Single-project scope** — Multi-project isolation deferred to later phase; current store uses a single `knowledge.db` per repository.
2. **No semantic retrieval** — Only deterministic filtering by metadata (type, status, authority). KnowledgeRetriever belongs to Phase 8.
3. **No graph traversal** — Relationship references stored, but graph traversal/contradiction detection belongs to Phase 3.
4. **SQLite file location** — `knowledge.db` stored in `artifacts/knowledge/` directory; path is deterministic but not yet configurable via `config/harness.yaml`.
