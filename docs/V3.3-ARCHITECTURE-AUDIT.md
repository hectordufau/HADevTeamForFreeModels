# V3.3 Architecture Audit — Engineering Knowledge & Decision Intelligence

**Date:** 2026-09-17
**Base:** v3.2.0 (729/729 tests PASS)
**Branch:** feature/v3.3-engineering-knowledge
**Auditor:** Hermes Agent (automated)
**Architecture Review:** APPROVED WITH REQUIRED ADJUSTMENTS (2026-09-17)

---

## 1. Executive Summary

V3.2 established a robust learning pipeline: execution outcomes → experiences → strategies → decisions, with strict COLD/LEARNED/TEST isolation, deterministic exploration, empirical baselines, and failure-derived learning. The system learns *what works* from execution evidence.

V3.3 extends the Harness to also learn *why things are the way they are* — the engineering history, requirements, decisions, debts, risks, and security constraints that shape the product. This is **Engineering Knowledge**: structured, queryable, graph-connected records that the Harness can reason about, not merely Markdown documentation for humans.

**Audit verdict:** The V3.2 codebase has **no engineering knowledge infrastructure**. There is no knowledge graph, no structured record types (PRD/NFR/DR/ADR/TDR/RSK/SEC/RCA), no provenance model, no authority levels, and no knowledge retrieval integration. The existing ADR support (`harness/memory/adr.py`) is a 22-line thin wrapper with no schema, no lifecycle, and no graph relationships.

However, V3.2 provides **strong foundations** to build on:
- ExperimentContext (validation_run_id, mode, task_id, execution_id, reproducibility_seed)
- Namespaced storage isolation (artifacts/v3.2/<run_id>/<mode>/<store>/)
- Hash-chain evidence integrity (EvidenceStore)
- Decision impact tracking with attribution (DecisionImpactTracker, AttributionResult)
- Failure-to-learning pipeline (FailureToLearningPipeline)
- Statistical evaluation with empirical baselines (EmpiricalEvaluator)
- Deterministic exploration with seed derivation

### 1.1 Architecture Review Outcome

The V3.3 architecture package was reviewed by the human architect. The review is **APPROVED WITH REQUIRED ADJUSTMENTS**. The primary scope is narrowed to **Engineering Knowledge & Decision Intelligence**. Learning Quality optimization (Experience Quality, Strategy Evolution, Adaptive Exploration, Continuous Learning, Cross-Task Generalization) is classified as **FOUNDATION_ONLY** and is a candidate for **V3.4 — Learning Quality & Optimization**.

## 6. New Core Components (Revised: EngineeringRecord Common Core)

The architecture review recommends a **common core** approach rather than eight independent persistence/lifecycle implementations. All record types share identity, provenance, authority, lifecycle, relationships, versioning, and validation through a single `EngineeringRecord` base.

```
EngineeringRecord (common core)
        │
        ├── ProductRequirement (PRD)
        ├── NFR
        ├── DecisionRecord (DR)
        │      └── ADR
        ├── TechnicalDebt (TDR)
        ├── Risk (RSK)
        ├── SecurityRecord (SEC)
        └── RCA
```

| Component | Package | Purpose |
|-----------|---------|---------|
| `EngineeringRecord` | `harness/knowledge/` | Base class with shared identity, provenance, authority, lifecycle, relationships, versioning, validation |
| `PRD` | `harness/knowledge/` | Product Requirement Document (with individually addressable REQ records) |
| `NFR` | `harness/knowledge/` | Non-Functional Requirement |
| `DR` | `harness/knowledge/` | Decision Record |
| `ADR` | `harness/knowledge/` | Architecture Decision Record (extends DR) |
| `TDR` | `harness/knowledge/` | Technical Debt Record |
| `RSK` | `harness/knowledge/` | Risk Record |
| `SEC` | `harness/knowledge/` | Security Record |
| `RCA` | `harness/knowledge/` | Root Cause Analysis |
| `KnowledgeGraph` | `harness/knowledge/` | Graph model with relationships |
| `KnowledgeStore` | `harness/knowledge/` | Persistence, indexing, integrity |
| `KnowledgeRetriever` | `harness/knowledge/` | Context retrieval, traversal |

**Key change from review:** Avoid eight independent persistence/lifecycle implementations. All record types share a common core with shared identity, provenance, authority, lifecycle, relationships, versioning, and validation.

## 7. Duplicate Concepts — Architecture Review Resolution

The architecture review re-evaluated the four reported duplicates. The original audit proposed collapsing or replacing; the review clarifies the correct relationship for each.

### 7.1 ADRAutomation vs DR/ADR

| Field | Value |
|-------|-------|
| **Classification** | OVERLAPPING RESPONSIBILITY |
| **Action** | ADRAutomation → adapt/migrate → new DR/ADR infrastructure |
| **Rationale** | Avoid maintaining two independent ADR systems. The existing `ADRAutomation` thin wrapper should be adapted to create full `DR`/`ADR` records in the new infrastructure, not maintained as a separate system. |
| **Migration** | `ADRAutomation.record_decision()` creates full `ADR` records; `get_relevant_adrs()` queries the knowledge graph. Old API preserved as compatibility shim. |

### 7.2 RootCauseAnalyzer vs RCA

| Field | Value |
|-------|-------|
| **Classification** | INTEGRATE — DO NOT COLLAPSE |
| **Rationale** | These are NOT the same abstraction. `RootCauseAnalyzer` is an analysis mechanism/service. `RCA` is a persistent Engineering Record. |
| **Relationship** | Failure → RootCauseAnalyzer → RCA proposal → review/policy → accepted RCA record |
| **Action** | Extend `RootCauseAnalyzer` to produce RCA proposals. The analyzer remains a service; the RCA remains a record. |

### 7.3 FailureLesson vs RCA

| Field | Value |
|-------|-------|
| **Classification** | RELATED — DO NOT MERGE |
| **Rationale** | These are NOT equivalent. `RCA` is an explicit engineering explanation of a failure. `FailureLesson` is a reusable learning representation derived from failure analysis. |
| **Relationship** | Failure → RCA → FailureLesson → StructuredExperience → Strategy |
| **Action** | Avoid duplicating the same textual content, but preserve semantic boundaries. RCA lives in Engineering Knowledge; FailureLesson lives in Learning. |

### 7.4 MemoryScore.source="adr" vs ADR

| Field | Value |
|-------|-------|
| **Classification** | REFERENCE — NOT DUPLICATE |
| **Rationale** | A memory reference or score associated with an ADR is not itself an ADR. The canonical ADR should live in Engineering Knowledge. Memory may reference/index it. |
| **Preferred direction** | EngineeringKnowledge ADR → reference → Memory / Retrieval metadata |
| **NOT** | Two independent ADR representations |

## 9. Three Kinds of Knowledge

The architecture review requires explicit distinction between three kinds of knowledge. They may reference each other but must not be collapsed into one storage model.

### A. Engineering Knowledge

**Definition:** What the project explicitly knows, requires, or decided.

**Examples:** PRD, NFR, ADR, TDR, RSK, SEC, RCA

**Characteristics:** Authoritative, versioned, lifecycle-managed, provenance-tracked.

### B. Learning Knowledge

**Definition:** What the Harness empirically learned from execution.

**Examples:** StructuredExperience, FailureLesson, Strategy, DecisionImpact, performance history

**Characteristics:** Empirically derived, confidence-calibrated, subject to revision.

### C. Evidence

**Definition:** What supports or proves claims.

**Examples:** Test results, verification results, benchmark results, execution artifacts, evaluation evidence

**Characteristics:** Immutable, hash-chained, reproducible.

## 10. Knowledge Precedence

The architecture review requires formalized precedence with explicit conflict semantics.

```
Governance
    ↓
Security Authority
    ↓
Authoritative Engineering Knowledge
    ↓
Accepted Engineering Knowledge
    ↓
Task Contract / Requirements
    ↓
Verified Evidence
    ↓
Learned Knowledge
    ↓
Exploration
```

### Conflict Semantics

| Conflict | Resolution |
|----------|------------|
| Learned strategy conflicts with Accepted ADR | Learned strategy cannot silently override ADR → conflict detected → proposal to supersede ADR → policy/review |
| Learning outcome contradicts SEC | SEC is authoritative; learning cannot override SEC; flag for review |
| Evidence contradicts Engineering Knowledge | Evidence is authoritative for factual claims; Engineering Knowledge record flagged for update |
| Exploration contradicts Governance | Governance is absolute; exploration is blocked |

## 20. Experimental Design

### 21.1 Experimental Boundary

V3.3 should eventually allow:

```
V3.2 Learning only (BASELINE)
     ↓
vs
     ↓
V3.2 Learning + V3.3 Engineering Knowledge (KNOWLEDGE)
```

This lets field validation measure the actual contribution of Engineering Knowledge. If Learning Quality is simultaneously redesigned, causal attribution becomes much weaker.

### 21.2 Primary Question

Does explicit Engineering Knowledge improve engineering decisions and traceability beyond V3.2 learning alone?

### 21.3 Required E2E Traceability Scenario

A release-critical scenario must demonstrate:

```
PRD → REQ → NFR → ADR → TASK → IMPLEMENTATION → VERIFICATION → EVIDENCE
```

plus TDR / RSK / SEC where applicable.

### 21.4 Required Historical Learning Scenario

Also demonstrate:

```
Failure → RootCauseAnalyzer → RCA → FailureLesson → StructuredExperience → Strategy → Future Task
```

## 22. Conclusion

The V3.2 codebase provides a solid foundation for V3.3. The learning pipeline, isolation infrastructure, evidence integrity, and statistical evaluation are all reusable. The main gap is the complete absence of engineering knowledge infrastructure — no record types, no knowledge graph, no provenance model, no authority levels.

The architecture review has narrowed the scope to **Engineering Knowledge & Decision Intelligence** and classified Learning Quality optimization as **FOUNDATION_ONLY** (candidate for V3.4). The revised approach:
