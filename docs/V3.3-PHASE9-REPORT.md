## 6. Knowledge Integration Architecture

### Selection Mechanism
```
Task Contract → TaskAnalyzer → Task Analysis → KnowledgeQuery → KnowledgeRetriever
    → EngineeringKnowledgeContext → KnowledgeAwareTaskAnalyzer
    → KnowledgeAwareWorkflowPlanner → Workflow Plan → WorkflowValidator
```

### Key Principles
- Engineering Knowledge may influence planning but does NOT bypass planning policy
- Knowledge remains declarative input
- CapabilityGraph remains separate from EngineeringKnowledgeGraph
- Knowledge does NOT select agents directly — capability-driven matching does
- Retrieved ≠ INFLUENCED: a record in context but unused is not a decision influence
- Planner does NOT mutate or create Engineering Knowledge
- Security precedence: Governance > Security Authority > Authoritative Eng > Accepted Eng > Task Requirements > Learned > Exploration

### Knowledge Influence
Every material planning decision influenced by Engineering Knowledge is traceable to:
- record_id, record_type, record_version
- authority, status
- decision (e.g., workflow_structure, capability_requirement)
- effect (e.g., required integration verification)
- reason

### Knowledge-Derived Capabilities
Declarative mappings from Engineering Knowledge to required capabilities:
- NFR category → capability (e.g., performance → performance_testing)
- SEC constraint → capability (e.g., authentication → security_verification)
- TDR debt type → awareness capability (e.g., code → code_quality_analysis)

### Security Precedence
- SEC records with ACCEPTED or AUTHORITATIVE authority are mandatory
- SEC protected knowledge cannot be dropped by ordinary ranking/budget
- Security constraints derive required capabilities
- Unsafe learned strategy cannot override SEC

## 7. PlanningContext

### Typed Separation
```python
@dataclass
class PlanningContext:
    task_contract: Any = None
    task_analysis: Any = None
    required_capabilities: List[str] = field(default_factory=list)
    engineering_knowledge_context: Optional[EngineeringKnowledgeContext] = None
    learning_context: Optional[LearningContext] = None
    policy_context: Optional[Dict[str, Any]] = None
    knowledge_influences: List[KnowledgeInfluence] = field(default_factory=list)
    knowledge_derived_capabilities: List[KnowledgeDerivedCapability] = field(default_factory=list)
    knowledge_gaps: List[KnowledgeGap] = field(default_factory=list)
    capability_gaps: List[KnowledgeGap] = field(default_factory=list)
    digest: str = ""
```

### Input Separation
- Task Contract: task definition
- Task Analysis: capability requirements
- Engineering Knowledge Context: PRD, NFR, ADR, TDR, RSK, SEC, RCA
- Learning Context: StructuredExperience, FailureLesson, Strategy
- Policy/Governance Context: governance rules

## 9. Gap Detection

### KNOWLEDGE_GAP
Referenced REQ/NFR/PRD does not exist in KnowledgeStore.

### CAPABILITY_GAP
SEC/NFR requires capability not in CapabilityGateway.

### Structured Gap Representation
```python
@dataclass
class KnowledgeGap:
    gap_type: str  # "KNOWLEDGE_GAP" or "CAPABILITY_GAP"
    record_id: str
    reason: str
    severity: str  # "critical", "high", "medium", "low"
```

## 10. Conflict Handling

### Unresolved Conflicts
- Unresolved authoritative knowledge conflict → BLOCKED / NEEDS_HUMAN
- KnowledgeConflictError raised before execution begins
- Fail closed: never choose newest, agent confidence, learned strategy, or faster plan

### Security vs Learning
- SEC protected knowledge cannot be overridden by learning
- Learning suggests strategy that conflicts with Engineering Knowledge → Engineering Knowledge wins

## 11. Determinism

### Restart Determinism

### Knowledge Version Attribution
