## 5. Graph Architecture

### 5.1 Node Model

Graph nodes are stable EngineeringRecord IDs (strings). Canonical record data remains in KnowledgeStore — the graph never duplicates complete records into graph state.

### 5.2 Edge Model

Edges are typed, directed references between record IDs using Phase 1 RecordRelationship types:
- REQUIRES, SATISFIES, DECIDED_BY, CONSTRAINED_BY, INTRODUCES, MITIGATES
- SUPERSEDES, CAUSED_BY, RESOLVED_BY, VERIFIED_BY, SUPPORTED_BY
- CONTRADICTS, RELATES_TO, DERIVED_FROM

Direction is explicit: `source_id —relation_type→ target_id`. Inverse traversal preserves canonical direction.

### 5.3 External Reference Model

External references (evidence IDs, capability IDs) are allowed as nodes. They are distinguished from internal EngineeringRecord references but not segregated — the graph is agnostic to record type. Evidence is referenced by ID, never duplicated.

## 6. Traversal API

### 6.1 Core Operations

| Operation | Description |
|-----------|-------------|
| `neighbors(record_id, relation_type, direction)` | One-hop neighbor IDs |
| `outgoing(record_id, relation_type)` | Outgoing edge targets |
| `incoming(record_id, relation_type)` | Incoming edge sources |
| `related(record_id, relation_type)` | Both directions |
| `traverse(start_id, options)` | Bounded BFS traversal |
| `path(source, target, options)` | Shortest path (BFS) |
| `ancestors(record_id, options)` | Nodes reachable via incoming edges |
| `descendants(record_id, options)` | Nodes reachable via outgoing edges |

### 6.2 Bounded Traversal

All traversal is bounded by `TraversalOptions`:
- `max_depth` (default 10): maximum hops from start
- `max_nodes` (default 1000): maximum nodes to visit
- `allowed_relations`: restrict traversal to specific relation types
- `record_types`: filter by record type
- `statuses`: filter by lifecycle status
- `authorities`: filter by authority level
- `direction`: "outgoing", "incoming", or "both"

### 6.3 Typed Traversal

Every traversal operation accepts `relation_type` and `direction` filters. The `TraversalOptions` class provides per-query typed filtering.

### 6.4 Deterministic Ordering

All queries return results sorted by (record_id, relation_type, record_type). No dependence on Python hash(), filesystem order, or set iteration.

## 7. Cycle Semantics

Cycles are NOT globally prohibited. Relation-specific constraints:

| Relation Type | Cycle Allowed | Rationale |
|--------------|---------------|-----------|
| SUPERSEDES | No | Causality: A supersedes B, B cannot supersede A |
| CAUSED_BY | No | Causality must be acyclic |
| RESOLVED_BY | No | Resolution must be acyclic |
| RELATES_TO | Yes | Symmetric, non-causal |
| DERIVED_FROM | Yes | Mutual derivation possible |
| REQUIRES, SATISFICES, DECIDED_BY, CONSTRAINED_BY, INTRODUCES, MITIGATES, VERIFIED_BY, SUPPORTED_BY, CONTRADICTS | Yes | Non-causal relationships |

Detection: DFS-based cycle detection with deterministic path reconstruction.

## 8. Supersession Semantics

### 8.1 Chain Traversal

`supersession_chain(record_id)` returns the linear chain: ADR-001 → ADR-004 → ADR-009.

`effective_record(record_id)` returns the last record in the chain (most recent effective record).

### 8.2 Integrity Enforcement

- **Mutual supersession**: A supersedes B + B supersedes A → SUPERSESSION_CONFLICT (HIGH severity)
- **Branching ambiguity**: A supersedes B + A supersedes C → SUPERSESSION_CONFLICT (MEDIUM severity)
- **Fail closed**: Ambiguous supersession returns None (no arbitrary resolution)

## 9. Contradiction Foundation

### 9.1 Detected Types

| Type | Detection Method | Severity |
|------|-----------------|----------|
| DANGLING_REFERENCE | Edge references nonexistent node | HIGH |
| INVALID_RELATION | Relation type not in VALID_RELATIONSHIP_TYPES | HIGH |
| FORBIDDEN_CYCLE | Cycle in SUPERSEDES, CAUSED_BY, or RESOLVED_BY | HIGH |
| SUPERSESSION_CONFLICT | Mutual supersession, branching ambiguity | HIGH/MEDIUM |
| EXPLICIT_CONTRADICTION | CONTRADICTS edge exists | MEDIUM |
| STATUS_CONFLICT | Superseded record still active/accepted | MEDIUM |

### 9.2 No LLM Semantic Detection

Contradiction detection is deterministic and structural only. No LLM inference, no semantic analysis, no keyword matching.

## 10. Integrity Validator

`validate_integrity(store=None)` returns a sorted, deduplicated list of `IntegrityConflict` objects.

```python
conflict = IntegrityConflict(
    conflict_type="SUPERSESSION_CONFLICT",
    records=["ADR-001", "ADR-004"],
    relations=[{"source_id": "ADR-001", "relation_type": "SUPERSEDES", "target_id": "ADR-004"}],
    severity="HIGH",
    reason="Mutual supersession detected",
)
```

### Fail-Closed Influence

A graph with unresolved integrity violations must not be presented as clean knowledge. `ContradictionDetector.is_clean()` returns False when conflicts exist. Future Planner/Reviewer components must check integrity before consuming graph data.

---

## 11. Graph Rebuild & Determinism

### 11.1 Rebuild Behavior

`EngineeringKnowledgeGraph.build_from_store(store)` reads all records and relationships via the public store API. Graph A → destroy → Graph B (same store) → logical Graph A == Graph B.

### 11.2 Restart Determinism

Process A creates records, persists, builds graph, records digest. Process B reloads store, rebuilds graph, records digest. Both digests match — no Python hash(), no filesystem ordering, no process-local state.

### 11.3 Graph Digest

Deterministic SHA-256 digest: sorted nodes + sorted typed edges → SHA-256. Two logically equivalent graphs always produce the same digest.

---

## 12. CapabilityGraph Separation

EngineeringKnowledgeGraph != CapabilityGraph:
- No capability classes imported
- No capability semantics stored
- Graph nodes are record IDs, not capability definitions
- No subclassing between the two

---

## 13. KnowledgeStore Integration

Graph reads from KnowledgeStore via public API (`list_all()`, `get()`). Does not bypass store validation by reading SQLite internals. Corrupt canonical records are detected and excluded.

---

## 14. Mutation Model

No independent canonical graph mutation. There must not be two truths: KnowledgeStore says edge does not exist but Graph says edge exists. The graph is a derived/cache state — rebuild from authoritative source.
