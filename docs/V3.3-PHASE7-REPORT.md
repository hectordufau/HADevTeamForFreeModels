## 4. RCA Schema

```yaml
id: RCA-001
title:
summary:
failure_ref:                    # Stable failure identity (required)
failure_type:                   # From FAILURE_TAXONOMY
symptoms: []                    # Observed symptoms
root_causes: []                 # Root causes (at least one required)
contributing_factors: []        # Contributing factors
impact:                         # Impact description
resolution:                     # Resolution summary
corrective_actions: []          # Fixes applied (at least one required)
preventive_actions: []          # Prevention steps (at least one required)
incident_id:                    # Associated incident ID
evidence_refs: []               # External evidence IDs (by reference)
related_failures: []            # Related failure IDs
related_decisions: []           # ADR/DR IDs
status: draft | analysis | corrective_action | preventive_action | closed
authority: proposed | accepted | deprecated | archived
provenance:
relationships:
```

### RCA Lifecycle
```
draft → analysis → corrective_action → preventive_action → closed
```

Invalid transitions FAIL CLOSED. Agent-generated RCA always starts as PROPOSED.

## 5. Architecture

### RCA Is Not the Analyzer
- `RootCauseAnalyzer` = analysis mechanism (service) → StructuredFailure
- `RCAAnalyzer` = RCA creation mechanism (service) → RCA (Engineering Knowledge)
- `RCA` = persistent Engineering Record (knowledge)

### RCA Is Not FailureLesson
- RCA answers: What happened? Why? What contributed? What corrected it? What should engineering change?
- FailureLesson answers: What reusable lesson should future decisions learn?
- A single RCA may generate 0..N FailureLessons.
- Derivation is explicit with stable provenance and authority separation.

### Failure Identity
- RCA references a stable failure identity (`failure_ref`)
- Survives process restart, persistence, RCA creation, learning conversion
- Does not rely on object identity, Python hash(), or process-local pointer

### Authority Separation
- Agent-generated RCA = PROPOSED (analysis confidence != Engineering Knowledge authority)
- RCA ACCEPTED does NOT automatically mean FailureLesson AUTHORITATIVE
- High-confidence FailureLesson does NOT upgrade RCA authority

### Security Precedence
- RCA-derived lessons cannot override SEC
- FailureLesson "disable certificate validation" + SEC → SEC WINS
- Security failures produce defensive-only lessons

### Cross-Domain References
- RCA references failures, evidence, and decisions by stable ID
- Does not embed or duplicate external records
- FailureLesson, StructuredExperience, Strategy remain externally owned

### KnowledgeStore Integration
- RCA uses existing KnowledgeStore (no independent RCA database)
- Typed field markers for RCA: `failure_ref`, `root_causes`, `corrective_actions`

### KnowledgeGraph Integration
- RCA relations with: ADR, TDR, RSK, SEC, external Failure, external Evidence
- Uses existing relationship types: RELATES_TO, SUPPORTED_BY, CONSTRAINED_BY

### ContradictionDetector Integration
- RCA supersession conflict (mutual supersession)
- Explicit RCA contradiction (CONTRADICTS edge)
- Invalid RCA state relationships (superseded but active)
- Security conflict (RCA-derived lesson vs SEC)

## 6. E2E Scenarios

### Standard Failure
FAIL-001 "API timeout" → RootCauseAnalyzer → RCA-001 "Connection pool exhaustion" → SUPPORTED_BY EV-001 → corrective: pool config → preventive: saturation monitoring → FailureLesson → StructuredExperience → Strategy.

### Engineering Impact
ADR-003 → failure → RCA-004 → RELATES_TO ADR-003 + INTRODUCES TDR-006 + RELATES_TO RSK-002.

### Security Safety
SEC-001 "TLS validation mandatory" + FAIL-SEC-001 → RCA-SEC-001 → FailureLesson proposal "disable certificate validation" → SEC conflict → BLOCK.

### Restart
Persist: Failure, RCA, FailureLesson, StructuredExperience, Strategy provenance. Restart. Verify complete provenance chain.
